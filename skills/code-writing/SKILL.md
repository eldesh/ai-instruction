## 基本原則

- 変更を加える前に、関連するコード、ドキュメント、規約、および制約事項を理解する。
- 単に差分（diff）を最小限に抑えるのではなく、意図された最終的な設計に合わせて最適化する。
- 求められている結果を得るために必要な変更のみを行う。
- 意図的に変更する場合を除き、既存の挙動を維持する。
- 不必要な抽象化や推測に基づく柔軟性よりも、シンプルで明確な解決策を優先する。
- 不確実性を隠さない。結果に影響を与える場合は、仮定や未解決の問題を明記する。
- その構成（construct）が何を表す/何に対応するモノかを責務とする。
  - どのように使われているか(使われる見込みか)を責務にしない。

## コードの構成

- ファイル、ディレクトリ、関数、型、モジュールなどの構成要素は、それぞれの責任を明確にして構成する。
- 構成要素のパブリックな兄弟同士（同じ親の子要素同士）は、同じ粒度の責任を割り当てる。
  - 例： 同じファイル内の公開関数、同じディレクトリ中の公開モジュールファイル、同じクラスの公開APIなど
- 役割がより明確になる場合は、コードを分割することを検討する。
- 現在の構造がコードの責任と一致しなくなった場合は、局所的な修正よりも、一貫性のある再構成を優先する。
- 所有権や境界が明確になる場合は、ファイルを追加、移動、または削除する。
- 識別子は正確で、ドメインに即したものを用いる。ただし必要十分な長さに抑える。
- 入力、出力、副作用が明確な小さな関数を優先する。
- 共通の概念が1か所で明確に表現できる場合は、重複を避ける。

## コメントとドキュメント

実装に関する自然言語による説明全般について、書くべきこと/書くべきでないことを定める。
ドキュメントにはREADME、PRの説明文、コードコメント、リファレンスなどすべてが含まれる。

- パブリックな動作、重要な不変条件、自明でない制約、および設計上の決定事項を文書またはコメントにする。
- 実装内容を単に繰り返すのではなく、意味、責任、または意図を説明する。
- 動作、インターフェース、ワークフロー、またはユーザー向けのサンプルが変更された場合は、適切なドキュメントを更新する。
- サンプルを正確に保ち、必要に応じて実行可能な状態を保つ。
- それがどのように使われているかを、使われる側のコメントに書かない。
  - どのように使うべきか、あるいは使えるかは書いてよい。
- 「以前のようでなくなった理由」を書かない。より簡潔な文章で現状を理解できる状態を目指す。
- 動作確認報告、テスト履歴、調査方法をコメントやドキュメントに書かない。

## コード編集

- タスクに取り組む際はTODOリストにこれから取り組むタスクを追加する。
  - TODOリストはファイルを作成してもチャットに書いても良いが、コミットはしない。
- タスクに取り組んでいる途中で、論理的に異なるタスクが判明した場合は以下の手順に従う。
  + 新しいタスクをTODOリストに追加する。
  + case
    * 現在のタスクが優先するべきなら、そのままタスクを完了する。
    * 他のタスクを優先するべきなら、現在の差分を破棄もしくはgit stashし、優先するべきタスクを始める。
  + 必要に応じてコミットを作る。（歴史は常に見直す）
  + TODOリストから完了したタスクを削除し、次のタスクに取り掛かる。

## バージョン管理

- 各コミットは、試行錯誤の経緯ではなく、意図した結果を反映した、首尾一貫した論理的な変更とする。
  - 最終的にそうなるなら、作業途中は適当な編集履歴として使ってもよい。
- コミットには、無関係な変更を含めず、作業途中で必要なことが判明した別の変更は現在の差分より前にコミットする。
- リファクタリングも最適化も「論理的な変更」に含める。つまり独立にコミットしてよい。
- 作業を始めた時点で未コミットの差分がある場合、その差分も含めてコミット履歴を作る。
- 履歴の編集が適切かつ安全である場合は、一時的な保存のためのコミット、自明な修正用のコミットを最終的な履歴に残さない。
- 明示的な許可がない限り、共有履歴を書き換えたり、既存の作業を破棄したりしない。
